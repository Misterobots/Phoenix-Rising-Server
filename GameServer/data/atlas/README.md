# Atlas data

Generated by `python -m tools.atlas` (see `GameServer/tools/atlas/README.md`). It covers every class in the 2.1.1
SDK dump, the Blueprints and data assets of every behemoth, weapon type and armor piece (with their perks, cells and
set bonuses), every item catalog, the loot, crafting, bounty, Hunt Pass and progression tables, and every island
spec and game mode, with generated sheets for each. Use the CLI to query it; this file describes the formats for
reading the files directly. To use the atlas for restoring content, start with `GameServer/tools/atlas/GUIDE.md`.

`verified.json`, `native_notes.json`, `topics/` and `candidates.md` (systems not yet written up) are hand-written.
`proposals/` holds our own proposed data, generated but not from the game. Everything else here is regenerated, so
do not edit it by hand.

Phoenix implementation overlays are documented separately from game-derived facts. `topics/adventure_island_map_contracts.json`
records offline-encoded island/map/arrival and deterministic encounter references. `topics/weapon_item_server_readiness.json`
records Phoenix implementation status, open client validation, and known runtime incidents with evidence and next checks.
`python -m tools.atlas plan <hunt> [--behemoth ROW] [--weapon TYPE] [--item ID]` joins those overlays with the
generated behemoth and item references. A source mapping is not an implementation claim, and an absent incident is
not proof that a composition works.

## classes/&lt;Class&gt;.json

Class names follow the engine: no C++ prefix (`MonsterPartComponent`), and Blueprints end in `_C`. Characters
that are not valid in file names become `_`.

| Field | Meaning |
|---|---|
| `name`, `kind` | Class name; `native` (C++) or `blueprint` |
| `parents` | Parent chain, nearest first |
| `size`, `sdk_header` | Class size and the SDK header that declares it (null if the SDK dump missed the class) |
| `package` | Blueprint package path in the paks |
| `properties[]` | `name`, `type`, `offset`, `size`, `flags` (UE property flags), `net` (replicated), `repnotify`, `onrep` + `onrep_source`, `rep_index` (Blueprint RepIndex), `schema_rep_index` (index in `data/2.1.1/layouts.jsonl`, the server's replication schema) |
| `components[]` | `name`, `class`, `source`: `property` (a component-typed property) or `SCS` (added in the Blueprint editor) |
| `functions[]` | `name`, `flags`, `params`, `ret`, `rpc` (`server` / `client` / `multicast` / null), `native`, `rva` (native thunk address); Blueprint functions add `bp_flags`, `statements`, `reads`, `sets`, `calls`, `authority`, `tables`, `assets` |
| `tables` | Data, curve and catalog tables the class or its functions reference |
| `game_data` | Files under `data/2.1.1` that name the class, with the number of matches |
| `pseudo_file` | The Blueprint code file in `pseudo/`, if the class has any bytecode |

Only the class's own properties and functions are listed. Inherited ones are in the parents' files
(`show --inherited` merges them).

## pseudo/&lt;Class&gt;.txt

Each Blueprint function as `=== Name` followed by its statements. `[n]` is the statement's byte offset and `@n` a
jump target. `self.X` is a property of the object itself. Calls appear as written in the bytecode.

## index_*.json

| File | Key -> value |
|---|---|
| `index_classes.json` | class -> `kind`, nearest `parent`, `package` |
| `index_who_sets.json` | property -> `Class.Function` entries that write it, and `Class (replicated, OnRep ...)` entries |
| `index_who_calls.json` | called function (`Class.Function` or bare name) -> calling `Class.Function` entries |
| `index_uses_table.json` | `<AssetClass> <name>` -> classes and functions that reference it |
| `index_native.json` | `Class.Function` -> native thunk address (offset from image base 0x140000000) |

## assets/&lt;name&gt;.json and .txt

Written by `python -m tools.atlas assets`. One file per package: `name`, `package`, `type` (main export class,
or `ClassDefaults` for a Blueprint package, with `class`), `refs` (other assets it references) and `exports`
(every export: `type`, `props`). Only values set in the cooked asset are present; inherited defaults are not.

The values are cleaned up but not changed. Struct field names lose their GUID suffix, references become
`Class name` (another package) or `@Export` (same package), blackboard keys become `bb.Key`, row handles
become `table[Row]`, and user-defined enum values use their display names.

The `.txt` view exists for:
- **Behavior trees**: numbered children in run order, with `[if ...]` decorators above the node and `{service ...}` lines.
- **Montages**: length, sections and notifies (start s, duration s, class, settings).
- **Data tables**: one row per line.
- **Physics assets**: bodies per bone.
- **Class defaults**: one value per line.

## index_assets.json

asset -> `type`, `package`, `refs`, `used_by` (assets, classes and `Class.Function` entries that reference it).

## behemoths/&lt;row&gt;.txt, behemoths.json and behemoths.txt

Written by `python -m tools.atlas behemoths`. The rows are the game's roster: `behemoth_metadata_table` and
`behemoth_asset_table` (129 rows, keyed like `lerawr_normal`). Each sheet has the roster values, the class
chain, the class defaults merged along it (nearest class wins, with the class that set each value), the action
set with each attack Blueprint's defaults, every action montage's damage windows and other gameplay notifies,
window and spawn requirements on archetype/classification evaluated (`[never here: ...]`, `[only when: ...]`),
what each attack spawns (per notify: classes and damage rows, marked `+` own table, `g` only in
`DamageTable_Generic`, `?` neither) with each spawned class's hit-related defaults, the damage table, the
behavior trees it reaches and its physics assets. `behemoths.json` has the same links per row, `spawned_classes`,
`rows_not_found` and a `missing` list; `behemoths.txt` is the coverage table, then the rows not found per
behemoth, then dumped tables and trees that no roster row reaches.

## weapons/&lt;key&gt;.txt, weapons.json and weapons.txt

Written by `python -m tools.atlas weapons`. One sheet per weapon type (`sword`, `axe`, `hammer`, `chainblades`,
`warpike`, `repeaters`, `strikers`, `bow`), `shared.txt` for what every type uses and `armor.txt`. Each type sheet
has, in order: its name prefixes and native `EWeaponType` value; its items (gameplay catalog: actor class, gear set, part slots and
default parts); its parts (`weapon_part_catalog` rows of its type: component class, granted abilities and buffs);
its `weapon_power_table` rows (power, element, granted abilities, and the type's own settings, shown where they
differ from the base row); the base weapon actor with its defaults; every skin weapon actor and what it sets;
then its classes grouped by kind (legendary part, part, ability, effect, buff, projectile, area effect, condition,
notify, anim blueprint, component, actor, interface, other) with their own non-cosmetic defaults and users; its
montages with each damage window (start, duration, notify class, damage rows, bodies); every damage row it names,
marked `+` (in a DamageTableData table), `~` (in one under another letter case; FName lookups ignore case), `?`
(in none) or `*` (a stem the notify completes with a charge or combo level), with the rows a spawner sets on a
spawned actor or a class sets in its own code; then its tables and other data assets.
`armor.txt` covers armor the same way: armor items (slot, class, set, set bonus, gear stat, perks per upgrade
level), set bonuses, gear stats, keyword perks and the cell effects they grant by rank, cell effects and the classes
they apply, cells, then the armor piece and cell classes by kind (how the game applies them: `topics/armor.md`).
`weapons.txt` is the prefix list and the coverage table; `weapons.json` has the same counts per type plus the
missing rows and classes without built code.

## items/, rewards/, islands/, items.txt, rewards.txt, islands.txt and areas.json

Written by `python -m tools.atlas areas`. Every dumped table is rendered row by row in the sheet for its kind:

- `items/`: `lanterns`, `quick_items` (quick items, flasks, grenades, consumables, boosts), `cells`, `materials`,
  `currencies_tokens`, `cosmetics`, `weapons_armor` (catalog view; per-type detail in `weapons/`), `other`.
- `rewards/`: `drops` (drop tables, bundles, containers, break rewards), `crafting` (recipes, recipe patterns, crafting
  and purchase unlock criteria), `bounties` (bounties and season challenges), `hunt_pass`, `progression`
  (experience, mastery, player journey, achievements), `other`, and `item_sources` (every item id these tables name,
  with the rows that name it).
- `islands/`: `hunts` (matchmaker hunts, island spec rows, schedules), `escalation`, `modes`, `specs/<island>.txt`
  (one per island spec asset: limits, kill rewards, content pools and the chooser tree down to behemoth rows, the
  hunts that use it and the server's `data/2.1.1/islands` contract), `island_specs`, `content_assets`,
  `hunt_modifiers`, `hunt_lists`.

Every area also has `classes.txt` (its Blueprint classes by kind, as in the weapon sheets) and `other_assets.txt`.
A table's values shared by at least 90% of its rows are printed once (`most rows:`) and the rows list only what
differs. Marks: `ITEM{catalog}` an item id and the catalog that has it, `table[Row]` a row found, `?` not in the
atlas, `<behemoths>` a behemoth with a sheet, `~` looks only (atmospheres, animations, UI, flare variants not
dumped); not dumped. `items.txt`, `rewards.txt` and `islands.txt` are the coverage tables (packages, classes, tables, rows,
links found/named, and every name not in the atlas); `areas.json` has the same per area.

## area_rules.txt and .json

Written by `python -m tools.atlas area-rules`: what the game allows in town (Ramsgate, the lobby) and on a hunt.
Three lists: every quick item and curiosity with whether it can be used in town (`CanUseInCity`, read through the
item's ability and its parent classes; `TOWN`, `hunt` or `?`), every Blueprint function that checks the area
(`IsInCity`, `IsInLobby`, `IsInIsland`, `IsInBountyFriendlyLocation`), and menu rows with area flags such as
`bDisableDuringHunts`. What the rules mean: `topics/area_rules.md`.

## damage_windows.json and .txt

Written by `python -m tools.atlas damage-windows`. `behemoths` maps a montage folder (`aq/lerawr`) to its
montages, each a list of windows in start order: `start` and `duration` (s), `class`, `roles` (weapon role ->
`bodies`, `skel_bodies`, `last_chance`), `keys` and `keys_after_first_hit` (damage table rows), `settings`
(only values that differ from `defaults`, the native DamageNotifyState defaults), and when set,
`requirements` (the non-empty parts of BehemothRequirements), `other` and `not_on_dedicated_server`.
The `.txt` lists the windows with non-default settings first, then every window.

## proposals/ (ours, not game data)

Rows or data this project proposes where the 2.1.1 client has none, each with a `.md` that says why and a
generator under `tools/atlas/proposals/` that derives every value from named game rows by stated rules. Nothing
here comes from the game. `proposals/beaver_frost_damage_table` fills the frost Gnasher's 17 missing damage rows.

## verified.json (hand-written)

`entries[]`: `id`, `fact`, optional `classes` / `props` / `functions`, `source` (commit, capture or file),
`date` (when it was confirmed). Add an entry when a behaviour is confirmed live or read directly from the game.

## native_notes.json (hand-written)

`notes`: `"Class.Function"` -> `{"summary", "details", "source", "date"}`. Add notes here after decompiling a
native function. For a function with no reflected name, use `"Class::Function @0xADDR"`, with the class name
written without its C++ prefix, so `show <Class>` finds it.

## topics/ (hand-written)

One Markdown write-up per game system, for when a question spans many classes, tables and native functions.
Each one gives the formulas, the tables and their values, what the server has to do, and what is still
unconfirmed.

| File | Covers |
|---|---|
| `topics/armor.md` | Armor resistances, the damage formula for hits on players, damage curves, pre-mitigation hooks, defence attributes, armor perks/cells, gear stats, set bonuses |
| `topics/behemoth_design.md` | One behemoth end to end (Embermane): classes and variants, action set, attack scoring, behavior tree, damage windows and rows, hitboxes, rage and stamina |
| `topics/behemoth_scaling.md` | Threat levels, tuning presets, behemoth health/stagger/damage scaling, power overrides, star levels |
| `topics/area_rules.md` | What is allowed in town vs on a hunt: quick items, cells, menus, bounty menus |
| `topics/repeaters_server.md` | What the server does for the repeaters and why, with evidence and dates; the checklist of what every weapon type needs on the server |
| `topics/weapon_power_and_abilities.md` | How a weapon finds its power row (by item id, which table) and where its abilities are granted (the pawn's ASC, slots) |
| `topics/sword_server.md` | What the server does for swords: the special (Overdrive, Feast), meter decay, dash cooldown |


## Adventure island map contracts

`topics/adventure_island_map_contracts.json` supplements the authored hunt/spec sheets with offline-extracted persistent map packages, player starts, streaming levels, arrival and atmosphere assets, patrol centers, and selected behemoth contracts for the 2.1.1 adventure islands. It records map-only previews and encounter blockers, and separates offline encoding from terrain/engine readiness and stock-client acceptance. This imported, source-backed review data is not generated by `areas.py`.

The same topic records the seven client-visible Hunting Grounds region labels from the installed English localization and links six regions to their localized island names, authored Adventure_Island hunt IDs, and map packages. `Ramsgate Outskirts` is retained as a client-visible label, but its exact player-hunt/map route is unresolved in the extracted 2.1.1 tables; the Island A starter/tutorial relation is marked as an inference, not a confirmed UI route.
